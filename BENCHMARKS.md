# SPT-3G D1 likelihood benchmarks

Performance record for the SPT-3G D1 standalone likelihood in `SPTLikelihoods.jl`.

## How to reproduce

```bash
julia --project=benchmark -e 'using Pkg; Pkg.instantiate()'
julia --project=benchmark benchmark/run_benchmarks.jl
```

The script writes [`benchmark/results.md`](benchmark/results.md) and then injects
it into this file and into `README.md`. Both documents quote that one file
verbatim, and `test/test_benchmark_docs.jl` fails if they drift apart, so a
number cannot be edited into either document by hand.

## Methodology

Two kinds of measurement are kept strictly apart, because they are not
comparable and cannot be produced by the same tool.

**Hot path — BenchmarkTools.** Repeatable operations are measured with
`@benchmark`, with `$` interpolation so that setup is never timed. Compilation is
excluded: every operation is run once before sampling begins. The prepared
Mooncake and ForwardDiff gradient calls carry mutable caches, so they are
sampled with `evals=1`; reusing a mutated cache several times inside one sample
would measure something other than a single gradient. Median and minimum,
allocation count and allocated bytes are all recorded.

**One-shot cold costs — fresh process.** Package load, artifact-backed
construction, the first compiled `predict`, and AD preparation happen once per
process and cannot be sampled repeatedly in a warm session. They are measured a
single time in a fresh child process by
[`benchmark/cold_prepare.jl`](benchmark/cold_prepare.jl), timed with `time_ns`
and `@timed`. These are **not** BenchmarkTools results and are never presented as
such: they have no median or minimum.

Resident memory is reported as peak RSS growth across a call, from
`Sys.maxrss()`, which returns the process peak rather than an instantaneous
reading. A step that does not push the process past a peak already reached
therefore shows no growth — that is the metric behaving correctly, not a missing
measurement, and it is why package load can report `0.0 MiB`.

The environment table records Julia and package versions, CPU, OS and kernel,
Julia and BLAS thread counts, and the input dimensions, so a future run can be
compared against this one on equal terms.

## Observations

1. **Production versus readable pipeline.** The fused production path
   (`predict` via `_fast_preinstrument_Dls` and `_fast_instrument_core`) is
   roughly 4× faster than the explicit ten-stage `foreground_stages` /
   `instrument_stages` pipeline and allocates about a quarter of the memory. The
   staged path is retained because it is readable and independently tested
   against candl at every intermediate stage; parity between the two is asserted
   at the baseline and all three nuisance multipoints.
2. **Data likelihood.** `loglikelihood(like, binned_theory)` costs well under a
   millisecond with six allocations, because the 1,392 × 1,392 bandpower
   covariance is Cholesky-factored once at construction and the factor is reused.
3. **Reverse versus forward mode.** The prepared Mooncake gradient over all 43
   nuisance parameters is about an order of magnitude faster than ForwardDiff and
   uses far less memory, which is what makes gradient-based sampling practical.
4. **The cold tape dominates.** Mooncake's `prepare_gradient` is by far the
   largest one-time cost, and it is why the preparation must be built once and
   reused. ForwardDiff preparation is effectively free, but its hot path is an
   order of magnitude slower.

## Optimisation ledger

Accepted optimisations, with the measurement that justified each. ForwardDiff
remained the correctness oracle throughout, and the full suite was re-run after
every accepted change.

| Change | Rationale | Before | After |
|---|---|---|---|
| Fused `_fast_preinstrument_Dls` / `_fast_instrument_core` production path alongside the staged pipeline | Staged pipeline materialises every intermediate 85,974-element vector | staged `predict` ≈ 12.2 ms, 32.00 MiB | fast `predict` ≈ 2.9 ms, 8.81 MiB |
| Cholesky factor precomputed and stored in `SPT3GD1Data` | Refactoring a fixed 1,392 × 1,392 covariance on every call | — | data-only `loglikelihood` ≈ 782 μs, 6 allocations |
| Analytical `ChainRulesCore` rules for `_fixed_covariance_solve` and `_fast_instrument_core` | Reverse-mode tape through the covariance solve and instrument core was the dominant Mooncake cost | — | hot prepared Mooncake gradient ≈ 29 ms vs ForwardDiff ≈ 323 ms |
| `bin_theory` switched from `vcat(bandpowers...)` to `reduce(vcat, bandpowers)` | Splatting made the return type infer as `Union{Vector{Any}, Vector{Float64}}` in a per-evaluation hot path | inference: `Union{Vector{Any}, Vector{Float64}}` | inference: `Vector{Float64}`, asserted by `@inferred` |

No optimisation in this ledger was accepted on tape size alone; each is justified
by a hot-path runtime or allocation measurement, and none regressed the hot
gradient.
